# LP 市场监控 3.0 · 模块化改造任务书（草稿，待 July 审）

2026-11-17 · Julywa · 研究机（tool-03）

3.0 现在把 6 块市场写在一个 836 行的 `mvp3/collect.py` 里，跑在两个进程中（08:20 三家、10:20 三家）。一家接口改了字段，同一进程里排在后面的几家当天都采不到。本任务只做结构改造：把 6 块拆成 6 个独立模块，各自取数、各自筛选、各自出文件、各自记版本；再加一个只读的整合层，把 6 个模块的结果汇成一份日报草稿。**规则和数据源都不改**：同一份上游数据进新旧两套代码，输出必须逐行相同。改造只在研究机做，完成后按发布包流程交回 1 号机。1.0、2.0 不动。

## 1. 目的与边界

**我在做什么**：给 3.0 做故障隔离和版本隔离，不扩协议、不改口径。

**最终目的**：
- 某个 DEX 或接口出问题，只有它那一块显示「失败」，其余照常产出。
- 每块能单独定位问题、单独回退到上一版。
- 产品第二阶段的飞书消息直接读整合层，不再读散落的文件。

| 做 | 不做 |
| --- | --- |
| 6 个模块拆分、模块输出契约、整合层（只落本地，并生成卡片 JSON 干跑） | 改任何门槛、meme、过滤、采全比规则 |
| 录制/回放工具，证明新旧输出一致 | 换数据源（候选方案只评估，见 §3.3） |
| 研究机 `com.july.lab.lp3-*` 自然运行 3 天 | 动 1 号机的代码、定时任务和状态 |
| 发布包 | 飞书推送、写表（含测试群：产品第二阶段再接） |
| | 1.0（`mvp/`）、2.0（`mvp2/`）和共享依赖 `v3/` |
| | 内部阶段 3 的收尾项（覆盖率自动重算、标签每周刷新） |

**与阶段 1、2 签收的关系**：两条线并行，互不阻塞。签收用 1 号机现有代码的产出（`fe9f8e2`）。改造代码要回到 1 号机重新影子运行 1–3 天，才能替换现有任务。

## 2. 模块划分

原则：一个模块 = 一个排序数据源 + 一个采全比分母 + 一份输出文件。

| 模块 | 内容 | 现有代码 | 定时（研究机） | 依赖的共享数据 |
| --- | --- | --- | --- | --- |
| `curve` | Curve · Ethereum | `curve()` + admin_fee 读链 | 08:20 | 股票名单 |
| `aero` | Aero + Aerodrome 旧版 · Base，用协议字段区分 | `aero()` + 按地址复查 | 08:20（与 `rh` 串行，顺序同现在：aero 先、rh 后；两者共用 GeckoTerminal 限速） | 股票名单、前一天本模块输出 |
| `rh` | Robinhood 主流对（Aero、Ramses、Uniswap 等多家），meme 另存 | `rh()` | 08:20 | 股票名单 |
| `orca` | Orca · Solana | `orca()` | 10:20 | 股票名单、Solana 标签 |
| `raydium` | Raydium · Solana | `raydium()` + 能定价一侧 | 10:20 | 同上 |
| `meteora` | Meteora DLMM + DAMM v2 · Solana | `meteora()` | 10:20 | 同上、前 7 天本模块输出 |

**为什么 Aero 和旧版不拆**：两者来自同一组 GeckoTerminal 请求，共用一个 DefiLlama 分母。拆开会让请求数翻倍，采全比也算不出来。

**为什么 Meteora 不拆**：DLMM 和 DAMM v2 的采全比分母在 11-16 已统一成一个。

**为什么 Robinhood 按链**：它只采主流对，meme 规则（非股票、非主流币即存档）是按链定的。

## 3. 数据源与稳定性（重点）

**结论：3.0 没有任何网页抓取，全部是 JSON 接口或链上只读调用。** 但稳定性不一样：3 家用官方 API；Aero 和 Robinhood 依赖第三方聚合 GeckoTerminal，这是最大的不稳定点。

### 3.2 改造中对稳定性的处理

- 每个模块输出里记 `source_health`：每个接口的请求次数、HTTP 状态分布、重试次数、是否走了兜底。
- 上游返回结构不对时，模块报「失败」并写明哪个字段，不用估算值顶替。
- 🔴 接口的模块在整合层单独标「第三方数据源」，读者能看出可信度不同。

## 4. 结构设计

### 4.1 目录（研究机）

```text
~/lp-lab/lp-research/              工作仓：从 ~/lp-lab/source 克隆，分支 lab/lp3-modular，基线 fe9f8e2
├── mvp3/                          原代码，不改，留作对照和回退
└── lp3/                           新代码
    ├── common/                    只放无业务规则的工具，带版本号
    │   ├── http.py                请求、重试（瞬时错误有限重试，400/404 直接失败）
    │   ├── refdata.py             读股票名单、Solana 标签缓存（只读）
    │   ├── coverage.py            采全比纯函数（从 llama_cover.py 搬过来，参数表移到各模块）
    │   └── contract.py            模块输出契约和校验
    ├── modules/<模块>/
    │   ├── source.py              只负责取数，返回上游原始结构
    │   ├── rules.py               本模块的筛选规则
    │   ├── config.json            门槛、meme、过滤参数，初始值与现在完全一致
    │   ├── VERSION、CHANGELOG.md
    │   └── test_*.py
    ├── run_module.py              跑单个模块：独立进程、超时、状态文件
    ├── orchestrate.py             按时段依次启动模块；一个失败不影响下一个
    ├── aggregate.py               整合层：只读各模块输出
    └── replay/                    录制、回放、新旧对比工具
```

### 4.2 隔离方式

- **进程隔离**：每个模块单独起一个子进程，有自己的超时（curve 15 分钟、aero 25 分钟，其余 5 分钟，参考现有耗时设定）。任何异常只让这个模块记「失败」，不再出现现在这种情况：`main()` 只拦 `SourceError`，其他异常会中断整个进程。
- **规则隔离**：门槛等参数复制到各模块的 `config.json`。改一家的规则只动这一家的文件，只跑这一家的测试。
- **数据隔离**：输出、状态、日志按模块分目录：`out/lab/lp3/<模块>/`、`~/.local/state/automation-lab/lp3-<模块>.json`。
- **版本隔离**：每个模块有自己的 `VERSION` 和 git 标签 `lp3-<模块>-vX.Y`，输出里写模块版本和提交号。回退一个模块，只需检出它的目录。
- **共享工具**：`common/` 改动要升版本号，并跑全部 6 个模块的回放。

### 4.3 模块输出契约

每个模块每天一个 `<模块>-<日期>.json`，字段在现有 `summary` + `rows` 的基础上增加：

| 字段 | 含义 |
| --- | --- |
| `status` | `ok` / `failed` / `partial`（部分接口失败但有数据） |
| `module`、`module_version`、`git_commit`、`schema_version` | 追溯用 |
| `window` | 采集开始和结束时间（精确到秒，新加坡时间） |
| `source_health` | 见 §3.2 |
| `rows` | 池级字段，与现在完全相同 |

meme 存档继续单独出文件。失败时写 `<模块>-<日期>-FAILED.json`，与现在相同。

### 4.4 整合层

- 输入：当天 6 个模块的输出文件。只读，不调用网络。
- 每个模块先过契约校验，不通过就标「失败」，原因写清楚；文件缺失标「暂缺」。
- 输出：`out/lab/lp3/digest-<日期>.{json,md}`，以及按飞书卡片结构生成的 `card-<日期>.json`（**只生成，不发送**）。
- 卡片怎么分组、分榜、字段怎么降级，属于产品第二阶段，届时另写任务书。本任务只保证整合层能读、能校验、能标缺失。

## 5. 怎么证明新旧一致

规则不改，所以判据是：**同一份上游数据，新旧两套代码输出的 `rows` 逐字段相同。**

1. **录制**：在研究机运行原 `mvp3/collect.py`，把它的网络调用换成「真实请求 + 存档」，得到当天全部上游原始响应。
2. **回放**：把原始响应分别喂给原代码和新模块，各自输出一份。
3. **对比**：逐池、逐字段比较。新增的追溯字段不参与比较。只要有一个字段不同，这个模块就不算通过。
4. **历史依赖**：Aero 复查要读前一天的输出，Meteora 从 11-19 起要读前 7 天，采全比 3 日均值要读前两天。研究机首次运行前，把 1 号机 11-12 起的 `out/mvp3` 快照复制到各模块目录作为种子，并记录来源。
